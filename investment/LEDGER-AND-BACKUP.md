# 真实账本、对账和完整加密备份

沿用 Start-Investment.cmd 和私有“账户与对账”页面。不新增任务、不接券商权限、不提交订单、不测试发送Bark。

## 本机真实文件验收需要什么

每家券商分别导出**同一可完整取得期间**的：

1. 逐笔成交/交割单：成交编号（非委托号）、交易/成交日期、证券、数量、成交价/金额、实际费用及分项。部分成交用各自成交编号。
2. 资金流水及分红/扣税明细：净发生额、收入/支出符号、实际到账/扣款日期、关联成交或分红事件号。分红权益/应收记录与实际到账分开。
3. 期初和期末日末持仓/资金快照：全部证券数量、可卖数量、持仓成本**金额及口径**、证券市值、账面总现金、可用资金、冻结资金。摊薄成本价不等于购入成本金额。

这些可以来自一个完整交割文件或多个原始文件。保留原件，只在自己电脑选择文件，不需发到聊天。旧历史持仓不是今天的账户证明；无法导出某字段就保持未知。暂不支持融资/衍生品账户完整收益，不能把筛选后的部分持仓称为账户全部资产。

页面提供“完整交割 / 仅成交 / 仅资金”和明确的资金符号选择。资金流水中的买卖交收必须有逐笔成交关联号，否则停止，避免与成交文件重复计入。两家独立适配版本和实际字段映射存入批次，但**仍未取得真实导出样本**，不宣称已适配其所有客户端版本。未识别业务、日期、单位、费用、负号均先停止，不针对单条答案硬编码。

标准字段：成交编号、交易日、成交日、成交时间、结算日、资金到账日、操作、证券代码、成交数量、成交价格、成交金额、总费用、佣金、印花税、过户费、其他费用、资金发生额、关联流水号、费用已含流水号、已实现盈亏。通用“日期”不会默认为实际到账日。原始姓名、账号和未映射列不保存；来源SHA256、映射、批次及确认信息保留。

## 计算和证据边界

- 期初日末到期末日末采用开区间/闭区间 `(期初,期末]`；同日基准不猜测盘中先后。资金按明确到账日记入，结算日不替代到账日。
- 数量：期初＋逐笔买入－逐笔卖出＋明确确认的股份变动。可卖数量和冻结资金只使用券商字段，不凭T+1推断。
- 成本：仅明确确认“含买入费的移动加权购入成本金额”时进行重放。买入费入购入成本；卖出费减净卖出所得；部分卖出按卖出前平均购入成本分摊。同日买卖按明确成交时间排序；缺时间或时间并列不能确定先后时暂停成本判断。未知费用、缺历史、负持仓均不补零。
- 现金：期初账面总现金＋区间已到账净发生额，与期末账面总现金比较。可用资金不冒充总现金。明确关联的实际交收覆盖成交推算现金，只计一次。
- 红利：应收税前金额、到账税前金额、到账净额、独立关联税逐项比较。已含费用/税款必须明确关联，疑似双扣列为待核对。未来可能补扣的红利税不假定为零。
- 收益：`期末净资产－期初净资产－外部净转入`，不再额外加一次已经进入现金的红利。另列价格盈亏变化、实际分红、税费、已实现/未实现，以及券商原报与重算差异。所有未解释差异阻断已验证总收益结论。
- 只有两端全部资产/现金证据和完整期间声明、数量/现金/分红对账都通过，才给出**所填期间**总收益。不是自开户完整含息收益，也不是历史策略完整含息回测。
- 无外部资金流时给区间收益率。有资金流时可给按日末流量加权的Modified Dietz**估计**；不冒充TWR或MWR。保留净资产、逐日外部现金流及期间接口，后续在现金流时点估值齐备后再计算TWR、具备完整时间现金流后再验证MWR唯一性。[GIPS关于外部现金流与TWR的说明](https://www.gipsstandards.org/standards/gips-standards-for-firms/gips-standards-handbook-for-firms/)
- 两家同期间、各自核对通过后才合并收益；不把跨账户资金移动当成盈利，不猜测行业穿透或投资预算。

快照推演project分别判断executions和cash覆盖。仅成交来源不充当到账现金，现金按cashDate入账，关联SETTLEMENT只替代对应成交现金一次；没有有效关联时记录问题并跳过。覆盖或到账证据不足时不输出完整现金桥接；资金桥接也不等于可用资金或账户总现金。

Windows权限须以NTFS DACL实测为准；POSIX模式位或chmod(0600/0700)不等于Windows DACL，也不能证明其他Windows用户无法读取。权限审计只读记录实际允许/拒绝、继承及所有者；本轮不修改ACL。具体账户身份和本机路径仅留在本机审计记录。

## 备份范围和兼容

新完整包：`goose-investment-encrypted` v1，内部 `goose-investment-full` v1；Windows记录清单 `goose-investment-ledger-state` v1。包含全部持仓快照、原始归一化事件批次（含旧v1和新v2）、撤销、期初/期末对账证据、成本口径、字段映射、来源SHA/版本/确认元数据，以及**当前浏览器同源**旧账本。记录逐文件SHA256与总清单指纹。

密码只在浏览器WebCrypto使用：AES-256-GCM、随机16字节盐/12字节nonce、PBKDF2-SHA256 600000次，头部元数据作为AAD，包内内容另做完整性校验。不自创算法，不将密码发送到Windows服务或持久化。[W3C Web Cryptography](https://www.w3.org/TR/webcrypto/)

**跨设备/跨端口的旧App无法自动读取**。可选择其已导出的旧加密备份并在浏览器本地解密，合并入新完整包；冲突会阻断。旧手机加密v1/v2仍可在新入口预览/恢复，只恢复其包含的手机数据，不会删除Windows账本。旧页面原格式与IndexedDB机制不改动。

不包含Bark/访问密钥、券商凭据、任务开关/投递防重记录、系统环境、原始券商文件或可重生成的行情/报告缓存。需要保留的原始券商文件仍由用户在本机保存。加密包请另存可信介质；丢失密码无法恢复。当前保护上限为Windows原记录合计12MiB/5000文件、完整明文24MiB；超出明确失败，绝不截断。

## 恢复安全

1. 浏览器先校验密码、AAD、内容版本、内部摘要，并预览手机冲突；电脑验证每条记录、文件SHA、总清单、关联撤销与合并后的有效账本。
2. 仅合并、无静默替换。同编号不同内容、语义重复、将撤销现有有效批次或改变现有有效持仓基准均阻断。预览后数据变化必须重做预览。
3. Windows先在同一受权限保护的私有目录暂存验证，一次目录改名原子发布；失败/中断暂存不被账本读取。原文件不覆盖。重复恢复幂等。手机使用原有IndexedDB事务与版本冲突保护。
4. Windows与浏览器没有跨设备事务；若Windows已追加、浏览器随后保存失败，会明确报告部分完成，可重做预览重试而不重复导入。不会以“全部成功”隐藏部分失败。

恢复测试仅在合成副本上进行。代码测试通过、真实券商文件核验、券商接口接入是三个不同状态。

## 后续接口

`ledger_accounting.reconcile_period`提供固定期间、成本、现金流、证据质量和逐项差异；`overview`只合并同期间已核对账户。量化模块可读取这些带来源字段，不改写原账户。下一批仍按原研究系统的独立回测/样本外框架处理分红与企业行为、成本、T+1/涨跌停约束、换手和合理基准，不拿本次账户对账替代策略验证。
