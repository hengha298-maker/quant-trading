# Tailscale 1.104.2 设备授权资格兼容说明

本说明对应真实 Windows 已返回的固定诊断码 `whois_machine_authorized_missing`。它记录兼容处理的依据和边界，不包含真实设备、账户、地址、文件路径或密钥。

## 已确定的问题

Tailscale v1.104.2 的 [`tailcfg.Node.MachineAuthorized`](https://github.com/tailscale/tailscale/blob/v1.104.2/tailcfg/tailcfg.go#L455) 是带 `omitempty` 的 Go `bool`。`whois` LocalAPI 将其查询到的 Node 直接放入 JSON 响应，没有另行补齐这个字段，见 [`serveWhoIsWithBackend`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/localapi/localapi.go#L556)。

官方历史提交 [`ab482118`](https://github.com/tailscale/tailscale/commit/ab482118ad7e04bcf871fffec0f880fe44429b5d) 为该字段加入 `omitempty`，并说明协调服务端计划将其清零，从而省略发送。这证明 peer 字段缺省不能一概解释为“设备未批准”。公开客户端源码不能进一步证明闭源协调服务端在这台真实设备上采用了哪一条内部路径，也没有发现客户端主动把 peer 的该字段改成 true 的行为。

反方向同样不成立：缺省也不能直接解释为 true。原来的单字段检查把“没有肯定证明”当成最终拒绝，无法兼容合法的省略响应；本次改为在限定版本、限定缺省场景中取得额外的当前网络资格证据。

## 可以使用的额外证据

官方 [Tailscale identity](https://tailscale.com/docs/concepts/tailscale-identity) 在“Identity's role in secure connections”中说明：启用设备审批时，批准前既不会把该节点公钥分发给其它设备，也不会把其它设备公钥分享给它。[Device approval](https://tailscale.com/docs/features/access-control/device-management/device-approval) 也明确，待批准设备不能在 tailnet 内发送或接收流量。[Node keys](https://tailscale.com/docs/concepts/node-keys) 说明节点公钥绑定设备与用户身份，并依据访问控制策略分发。

因此，限定兼容路径需要同时验证以下证据，不能只依据设备名称或 IP：

- 已核对本机 CLI 版本恰为 1.104.2，且 `MachineAuthorized` 是缺省；显式 false、null 或其它类型仍拒绝。
- 每次重新读取本机 daemon 的 `status --json`，本机保持 Running、在线且当前所有者一致；选定 peer 的稳定 ID、iOS 类型、用户 ID、登录名和完整直接 IP 集合均一致。
- peer 的 `InNetworkMap` 和 `Online` 都必须严格为 true；`whois.Node.Key`、status Peer 映射键、`Peer.PublicKey` 必须是完全相同、格式正确且非零的节点公钥。
- 所有原有逐字段 whois 检查继续执行，包括稳定 ID、用户、登录名、精确主机 IP、非共享、非标签、有效期和未过期状态。被隔离或仅获 PeerAPI 权限的节点也拒绝。
- 每个实际读取请求仍必须来自既有 Tailscale Serve 私网 HTTPS 代理，经过 loopback 后端、随机后端路径和严格代理请求头检查，再完成上述身份核验、一次性配对与短期会话核验。

这条路径验证的是当前受信任 Tailscale daemon 所持网图中的节点密钥和网络访问资格，没有把缺失字段改写为 true，也没有添加任何用户输入的“已批准”开关。未知版本的缺省响应仍失败关闭；CLI 失败、超时、格式错误或任一不一致也失败关闭。额外读取结果不缓存。

启动前的 `identity_failures` 只返回资格检查结果，不返回可访问资产的身份绑定。即使附加证据齐全，直接调用 `verify_identity` 仍以 `whois_authorization_requires_serve` 拒绝缺省场景。只有请求先通过全部既有 Serve 来源、HTTPS、代理头与指定设备检查，内部调用才可凭已核验的 Serve 上下文完成缺省兼容；之后仍需通过配对或短期会话检查才能读取资产。这使“允许启动受保护的分享入口”与“允许某个实际手机请求读取”保持明确分离。

## 为什么不能只看 InNetworkMap

[`PeerStatus.InNetworkMap`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnstate/ipnstate.go#L324) 只表示节点出现在最新网图，`InEngine` 和 `InMagicSock` 也只表示被相应组件跟踪。它们没有独立的管理后台批准布尔语义。

[`UnsignedPeerAPIOnly`](https://github.com/tailscale/tailscale/blob/v1.104.2/tailcfg/tailcfg.go#L488) 节点可以存在网图中，却只有受限 PeerAPI 权限；[`IsJailed`](https://github.com/tailscale/tailscale/blob/v1.104.2/tailcfg/tailcfg.go#L549) 节点不应主动建立连接；过期节点也可能仍在网图中。因此兼容检查要求密钥、身份、状态及限制标志一起满足条件，且实际 Serve 连接仍受端口访问策略约束。

## HTTPS 与真实请求的边界

官方 Serve 代码使用真实连接上下文设置 `X-Forwarded-For`，并依据 TLS 设置 HTTPS 标记；它清除客户端伪造的 Tailscale 身份头，再用源地址 whois 设置登录身份，见 [`addProxyForwardedHeaders` 与 `addTailscaleIdentityHeaders`](https://github.com/tailscale/tailscale/blob/v1.104.2/ipn/ipnlocal/serve.go#L1088)。Funnel 请求有单独标记，本项目继续拒绝 Funnel。

入站 WireGuard 流量还需要通过 Tailscale 包过滤，见 [`filterPacketInboundFromWireGuard`](https://github.com/tailscale/tailscale/blob/v1.104.2/net/tstun/wrap.go#L1128)。源码中的 PeerAPI 特例不是任意 Serve 端口的放行路径。启动前检查只确认分享的设备资格，不能单独证明 iPhone 到 Windows 的 DNS、TLS 或端口已经连通；实际手机请求通过后才形成入站证据。Windows 本机 HTTPS 自检不作为手机入站证据。

## 证据的实际限制

`status --json` 的“重新读取”是重新向本机受信任 daemon 查询，不是向管理后台申请新的独立审批证明。网图与撤销仍依赖 Tailscale 控制面同步；官方 [key management](https://tailscale.com/blog/tailscale-key-management) 说明，网络分区时客户端可能暂存密钥。本项目要求本机在线、每请求重新核验，并在检查失败时停止分享和撤销会话，但不能宣称消除了底层 VPN 控制面的一切传播延迟。

本说明所述依据来自官方文档及固定 v1.104.2 源码。自动化用虚构数据验证合法缺省、显式拒绝、身份与密钥不一致、CLI 失败和原有 HTTPS/配对边界；这类验证不能替代真实 Windows 与 iPhone 的最终访问。新版本实机成功前，不应把“模拟测试通过”写成“真实手机已连接成功”。真实 P1 数据仍仅从用户明确选择的本地文件读取，沿用原有校验；本兼容工作不修改持仓原文件，不上传资产，也不改动 V1.1、Bark 或定时任务。

直接相关的 Go 实例是 golink 的 [`defaultCurrentUser`](https://github.com/tailscale/golink/blob/e034189e44e1d01c0672c401b038b8959d58aea6/golink.go#L1048)：普通模式以真实连接的 RemoteAddr 调用本机 LocalAPI WhoIs，服务模式才接受 tsnet 内部 loopback 代理注入的身份。该身份函数不把 peer 的 `MachineAuthorized` 布尔值作为准入依据。它验证的是用户身份，不能直接替代本项目“仅指定 iPhone”的设备绑定；其中允许未知用户或 whois 失败后保留头部身份的选项也没有被本项目采用。

本项目继续使用已安装官方 CLI 调用同一 daemon 的 whois 与 status，保留 Python、Windows 启动器和原有 Serve 架构。与 Go 的类型化 LocalAPI 相比，CLI JSON 需要由本项目明确区分字段缺省、null、类型错误和版本语义，所以本次只增加固定版本兼容验证及回归测试，没有复制 golink 的授权分支，也没有引入新的认证代理。

对照范围同时核对了 [Pomerium 自述](https://github.com/pomerium/pomerium/blob/main/README.md)及 [Authelia 官方 Tailscale OIDC 集成](https://github.com/authelia/authelia/blob/a72665715bd3614d5cb9e5947789566e1a63a1cf/docs/content/integration/openid-connect/clients/tailscale/index.md)。它们有明确许可证且近期更新，但不是当前 `MachineAuthorized` 缺省响应的替代实现，本轮不展开部署或架构改造。
